# Mission Control v1 — real guest execution, explicit verification scope

Mission Control is a prompt-first interface over the actual bundled RESIDUAL
repository. It is not a desktop simulation, a hosted SaaS backend, or a replacement
for Factory/M4. The original `demo` is still an explicitly scripted tutorial.

## Visitor workflow

1. Open `/demo/`; wait for `LINUX · READY`. Choose Mission or Terminal.
2. **Without a model:** choose Repository audit, select actual repository files,
   and run. Source hashes, line counts, TODO/FIXME locations and Python syntax /
   top-level symbols are computed in the guest and checked by the real Harness.
   An audit reports syntax failures; a contract pass means the inventory matches
   its inputs, NOT that the repository has no bugs or vulnerabilities.
3. **Live prompt:** Connect provider opens `/provider/` outside the WebVM service
   worker scope. Load Puter, then click Sign in separately. Keep that tab open.
   Back in Mission Control, enter a prompt, choose sources and budget, and consent
   to exporting those source snapshots. Click Run mission. There is no implicit
   tutorial-provider fallback. Model availability/credit errors remain failures.
4. Inspect live ledger events, the answer, receipts, cost/usage UNKNOWNs and result
   binding. Download the evidence JSON, or inspect the same `runs/missions/<id>/`
   files from the terminal. Nothing generated by the model is executed or merged.

Example real work: explain a component from selected source files, draft an
implementation plan, create a source-grounded review checklist or Markdown
artifact, or run a deterministic inventory of files you edit in the terminal.
Free-form prompts cannot currently invoke arbitrary tools, run generated code,
apply patches, or launch full Factory swarms. That requires a separately qualified
execution adapter and sandbox, not a fake progress animation.

## Shared CLI

```
mission audit --stream --files README.md residual/cli.py
mission inspect runs/missions/<mission-id>
python3 -m residual verify-trace runs/missions/<mission-id>/trace.jsonl --result runs/missions/<mission-id>/result.json
```

`mission` aliases `python3 -m residual.workbench`. A CLI audit with `--stream`
projects its actual ledger into Mission Control. Existing `residual run ...
--config ...` remains available for custom tasks/providers; it is not implicitly
visualized unless run through the workbench adapter. After reload, use the CLI to
inspect saved runs; auto-restoring a Mission Control history is not implemented.
The guest overlay survives normal reload on the same image/browser. A new image
has a new overlay namespace: download important evidence before upgrading/resetting.

For locally configured providers (no browser dependency), create `mission.json`:

```json
{"prompt":"Explain the selected component and draft a review checklist.","mode":"live","files":["residual/cli.py"],"max_calls":2,"max_output_tokens":1024,"required_text":["Review checklist"],"cloud_consent":false}
```

```
python3 -m residual.workbench run --request mission.json --config provider.toml
```

Use an explicit local provider configuration. Remote export needs
`cloud_consent:true`; missing configuration never means scripted inference.

## Architecture and boundaries

The UI writes JSON into a CheerpX DataDevice and invokes a fixed Python module
using an argv array. No user prompt, model text, or file path becomes shell code.
The same Linux instance, repository, Python Harness and writable overlay serve
both surfaces. Source text is frozen into `task.json` before dispatch. The adapter
registers its own mechanical checks and uses existing Harness acceptance and
hash-linked evidence without changing shared schemas or M4 trust-boundary code.

UI events are bounded OSC projection frames copied from the real ledger. They
are not new trusted receipts or a second evidence chain. The UI is not a security
boundary against a user who controls this disposable guest/origin. Final integrity
checks call the existing verifier and bind the persisted result to the terminal
ledger commitment. `externally_anchored:false` is intentional.

For live answers the contract requires a bounded nonempty answer, optional literal
acceptance strings, and exact quotations within frozen source line ranges. This
checks quote identity, not whether a quote supports the claim or whether an answer
is correct. **Semantic verification stays UNKNOWN**, even when mechanical checks
pass. Cost remains unknown without reported usage AND pricing; zero billed dollars
are never inferred from missing provider billing data.

## Provider repair

The previous button loaded a SDK asynchronously and then opened sign-in inside a
cross-origin-isolated WebVM page. Popup user activation and COOP/opener behavior
make that fragile. The new helper has no VM service worker and uses a separate
sign-in click before any await. An ephemeral 256-bit BroadcastChannel name passed
in the fragment connects same-origin tabs; no opener or auth-token forwarding is
needed. SDK failures, blocked/cancelled sign-in and heartbeat loss are visible.
Only an explicitly authorized mission grants inference, capped at three calls,
1536 output tokens per call, bounded request/response sizes and a guest wall limit.
Cancellation stops new work and response acceptance; a remote request already
sent can still finish and incur charges.

This shares GitHub Pages' origin trust. It is NOT hardened multi-tenant isolation.
Client/guest quotas can be bypassed by someone modifying their own browser. No
shared server API key is shipped. Puter authentication is NOT a RESIDUAL account.
Signup, durable storage, enforced admission/rate limits, concurrency accounting,
server-side cancellation, billing and abuse controls are a later backend milestone.
No public funded service should be launched with these browser-only counters.

## Evidence / claim discipline

Unit tests exercise real Harness rejection/retry, frozen sources and trace binding.
They use explicit mailbox response doubles where remote output is required.
Browser acceptance boots the real guest, runs arbitrary-source audits, executes
GUI missions, checks GUI/CLI file equality and reload persistence, and tests
provider setup isolation, SDK failure recovery, user-gesture popup behavior and
mailbox transport with a **Playwright SDK test double**. No production fallback
or test-mode switch exists in the application. Reports explicitly distinguish
these contract tests from real Puter authentication or paid inference.

A successful deployment plus these tests does not qualify real-account cloud
inference. That gate needs a user-authorized sign-in and real provider response,
followed by the same trace/result checks. Safari and physical mobile devices are
not certified by a narrow Chromium viewport. Do not use workflow color alone as
proof of model work, guest execution, or semantic correctness.
