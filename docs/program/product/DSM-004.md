# DSM-004 — ownership, fencing and replay protocol

**Status: proposal v1; implementation qualification pending.** Baseline and scope:
[program README](README.md). Normative statements below are release requirements,
not claims that the current interfaces already enforce the complete protocol.

## What the code currently establishes

| Surface | Observed behavior | Boundary still open |
| --- | --- | --- |
| `residual/factory/runtime_journal.py` / `RuntimeJournal` | File-backed SQLite, FULL synchronous transactions, contract before spawn, increasing per-plan/task lease generation, unique worker/attempt/lease/workspace IDs, append-only event triggers, chain check on reopen | One local journal; no distributed lease service or cross-store commit |
| `residual/station/store.py` / `Store` | Transactional task claim, random lease, expiry and heartbeat checks; interrupted local work becomes blocked at startup; task state is guarded by transitions | Separate Station and M2 ownership domains; no unified fencing epoch checked by every writer |

## Authority and ownership

The **authoritative store**, not the coordinator's memory, issues a monotonically
increasing `station_epoch` and per-task `lease_generation`. One owner may propose
accepted-state transitions for `(project_id, mission_revision_hash)` at a time.
Workers only submit immutable proposals. Schedulers choose placement/capacity;
metrics and observer cursors confer no authority. M4 alone evaluates the acceptance
conditions, and its host publisher performs the fenced state transition.

Every authoritative write MUST carry `(project_id, mission_revision_hash,
station_epoch, lease_generation, attempt_id, operation_id, payload_hash)` plus
authenticated caller identity. A writer checks ownership **in the same transaction
as the write**, including expected previous accepted-head hash. An expired lease
or minority partition cannot create an acceptance, even when an old worker is
still running. Lease expiry uses the authoritative service's time domain; process
kill ownership uses pidfds where available. Wall-clock rollback must not prolong
authority. Epoch advancement fences old owners independently of physical shutdown.

Lease acquisition and renewal MUST be durable before returning acknowledgement.
No lease token, textual worker assertion, provider capability string or monitor
health metric substitutes for the stored ownership check. A stopped task may retry
with a new attempt identity and greater generation, retaining the old outcome.
A retry may not reuse a prior verifier result after inputs, tree, policy or revision
change. A revised mission creates a new hash-linked revision, not mutable history.

## Publication and duplicate-delivery rules

1. Persist immutable candidate artifacts and verification evidence by digest.
2. Persist a prepared publication binding verified tree, integration receipt,
   expected accepted-head, owner epoch and a stable `operation_id`.
3. Atomically compare-and-swap the accepted-head and record its durable decision.
   This commit is the sole linearization point for acceptance.
4. Publish notifications through a transactional outbox; acknowledge consumers
   after their durable processing succeeds. Readers can reconstruct from the log.

A repeated operation with identical ID **and** payload digest returns the original
durable decision. The same ID with a different payload is an integrity error.
Delivery is at least once; accepted-state effects are idempotent only within the
stated authority store and operation namespace. There is no claim of exactly-once
network delivery or arbitrary external side effects. An external action requires
its own idempotency key/receipt and reconciliation; an ambiguous action result is
UNKNOWN until resolved.

The protocol intentionally does not prescribe a transaction spanning Git and
SQLite. Immutable Git objects can be prepared before the store commit; the
acceptance record must bind object/tree digests, retain the objects, and publish
only after the authoritative transaction. A crash can leave orphan prepared
objects, which are not accepted state. A visible Git branch must be treated as a
projection unless its update participates in an equivalent fenced protocol.

## Cursors, crash and replay

Consumer identity and stream identity scope each cursor. A delivery carries its
first/last sequence and content digest. An acknowledgement MUST reference a
persisted delivery, cannot skip an unprocessed gap, and cannot exceed the delivered
or durable stream head. Store the consumer effect and cursor atomically, or use
an idempotent inbox before advancing the cursor. Reset requires an audited operator
action; redelivery never creates a second acceptance. Polling and report generation
are read-only unless explicit acknowledgement is requested.

On restart, validate schema, chain roots, object availability and owner epoch before
readiness. Fence the previous owner, recover the last committed accepted-head,
classify unfinished attempts, and replay unacknowledged deliveries. If verification
completed but publication did not commit, retain prepared evidence and re-admit it
under the new epoch/current policy; never infer acceptance from a process exit code.
If publication committed but the reply was lost, return the stored decision.

## Required protocol qualification cases

| Case | Required result / retained proof |
| --- | --- |
| Owner paused past lease; replacement starts | Old owner's write rejected; generation and epoch recorded |
| Partition between quorum check and append | Write-time fencing rejects minority; preflight quorum check alone insufficient |
| Two candidates share expected accepted-head | At most one CAS succeeds; loser remains unaccepted |
| Duplicate same operation/digest | Original receipt and accepted transition returned; count unchanged |
| Duplicate operation with changed digest | Integrity error; no effect |
| Ack future, undelivered or gapped sequence | Rejected; durable cursor unchanged |
| Crash after each publication step | At most one accepted transition; evidence remains traceable |
| Restart after ack lost | Consumer redelivery is harmless and durable effects not repeated |
| Disk-full/partial write/quorum loss | No positive acknowledgement before durable commit |
| Clock skew/rollback and stale cached lease | No acceptance based solely on local expiry calculations |

Each case retains source SHA/tree, seed/schedule, authority log, exact before/after
accepted-head, event/receipt digests, lease generations, and a model-free replay
command. Implementation follows the stable M4 API after #81 qualification.

## Explicit non-promises

Residual does not implement Byzantine consensus, tolerate a compromised authority
store/host, make SQLite files safe to share as a distributed database, ensure
unbounded availability during partitions, or make arbitrary external side effects
exactly once. Production multi-node mode requires an independently qualified,
authenticated consensus/storage backend plus tests of this integration protocol.
