The R4 run qualified candidate parent `eada7577cf6f2de875b508c6a82f47870e3aa673` with tree `f4d144a28166f03aecefa9e27ebaca7b4c621ebe`. Fifteen of seventeen gates passed; R4-G11 and R4-G13 failed, producing the overall disposition `BLOCKED`.

R4.1 separated those failures by failure domain:

- **R4-F01** was a G11 qualification-instrumentation defect. The harness read a stale task snapshot rather than the authoritative Station task state.
- **R4-F02** was a G13 candidate-protocol defect. Receiver-side idempotency prevented a duplicate receiver event, but the restarted sender retransmitted before reconciling an already committed operation.

The qualified R4.1 candidate is `8701367db6d3202f24b3eb9f4696b0cadf657985`, whose parent is `eada7577cf6f2de875b508c6a82f47870e3aa673` and whose tree is `79bfe6ed1743907065ed44aeb9c460c47527e0c6`. ## R4-F01: G11 qualification instrumentation defect

### Hypothesis

The G11 failure did not demonstrate a candidate security-boundary failure. `Station.prepare()` persisted `candidate_dir` into authoritative task storage while returning an earlier task snapshot. G11 then attempted to read `work["task"]["candidate_dir"]` from that stale return value.

### Observed evidence

The R4 traceback terminates at the harness expression used to construct the sentinel path and reports `KeyError: 'candidate_dir'`. This occurred before G11 could test the intended protected-path boundary, so the failed gate could not support a candidate-security conclusion.

The R4.1 G11 result records both intended negative controls:

- a protected-path write was rejected with `ContractError: Candidate must only update explicitly writable task files`;
- a malformed tool envelope was rejected with `ContractError: Runner response must contain exactly the files object`.

For both controls, the before and after SHA-256 of the protected sentinel was `962f85a27854336f3286ad54b49321f62525043b5f3508b2ecc887fdd6e7550e`, and `unchanged` was `true`.

### Repair

The R4.1 harness reloads authoritative Station task state after `Station.prepare()` before resolving `candidate_dir` and constructing the sentinel. This was a harness-only correction to the measurement path; it was not a candidate security repair.

### Validation

R4.1 G11 passed against the real Station candidate boundary and disposable protected-path sentinel. The result supports the bounded conclusion that the corrected instrumentation exercised the intended controls and observed no sentinel mutation.

### Architectural implication

A command result and the authoritative state it mutates are separate observation surfaces. Qualification code must not assume that a returned task object is a post-commit snapshot unless the interface explicitly guarantees that property. Security-gate instrumentation should re-read the authoritative state before deriving paths or assertions from persisted mutations.

## R4-F02: G13 candidate protocol defect

### Hypothesis

Receiver-side idempotency is insufficient to establish sender-side crash/restart reconciliation safety. After an ambiguous delivery outcome, a restarted sender must reconcile the operation against an authoritative receipt before it can decide whether retransmission is necessary.

The original observed sequence was:

```text
remote commit
→ ACK lost
→ sender restart
→ POST before reconciliation
```

The receiver emitted exactly one event because server idempotency suppressed a duplicate logical commit. That observation establishes bounded receiver deduplication for this operation; it does not establish that the sender avoided retransmission or correctly resolved its durable local state before sending again.

The stronger required invariant was:

```text
remote commit
→ ACK lost
→ sender restart
→ authoritative receipt lookup
→ recover receipt locally when present
→ zero retransmission
```

### Observed evidence

In the R4 G13 artifact:

- `network_actions_after_restart` was `[["POST", "comms"]]`;
- `lookup_first` was `false`;
- `no_post_before_lookup` was `false`;
- `receiver_event_count` was `1`;
- the local outbox eventually became `ACKED` with the receiver receipt.

This is the counterexample: eventual local ACK and exactly one receiver event coexisted with a sender retransmission before reconciliation.

In the full R4.1 G13 artifact:

- `network_actions_after_restart` was `[["GET", "comms/receipt"]]`;
- `lookup_first` was `true`;
- `no_post_before_lookup` was `true`;
- `receiver_event_count` remained `1`;
- recovery reported one ACKed, zero pending, and zero stale records.

### Repair

The candidate restart-recovery protocol was changed to reconcile each ambiguous pending operation through authoritative `GET comms/receipt` before any retransmission decision. A found receipt is persisted locally as the ACK. An absent receipt permits the original operation to be posted. If reconciliation is unavailable, the operation remains pending and is not posted.

### Validation

The sealed R4.1 record preserves five validated branches:

| Branch | Expected and observed action trace | Result |
|---|---|---|
| Receipt found | `GET → ACK`; zero `POST` | PASS |
| Receipt absent | `GET → POST → ACK` | PASS |
| Reconciliation unavailable | remain `PENDING`; zero `POST` | PASS |
| Restart repeated after reconciliation | zero network action | PASS |
| Full R4.1 G13 qualification | receipt lookup precedes any retransmission decision | PASS |

The full gate artifact directly records the receipt-found branch and its network trace. The ready-for-canary seal records all five branch outcomes. This distinction is retained so that the summary does not imply that every branch has a separate artifact in the final G13 directory.

### Architectural implication

End-to-end delivery safety spans distinct invariants:

1. receiver idempotency constrains duplicate receiver-side effects;
2. durable sender state preserves unresolved intent across process failure;
3. authoritative reconciliation resolves ambiguous outcomes after restart;
4. fail-closed retry ordering prevents retransmission when reconciliation cannot establish absence.

The first invariant cannot substitute for the other three. Exactly-once receiver observation in one run is therefore not evidence of zero retransmission, and it is not by itself evidence of sender-side crash/restart safety.

## Limitations

- The findings are bounded to the recorded candidates, harness versions, Station implementation, loopback environment, and fault schedules.
- The R4.1 G13 artifact directly exposes the receipt-found trace. The other three branch-specific action traces are summarized by the sealed record rather than independently reproduced in this documentation lane.
- A single full qualification pass does not estimate long-run failure probability, performance under high concurrency, partition-duration sensitivity, or behavior with multiple senders sharing an operation identifier.
- The result does not establish universal exactly-once delivery semantics. It establishes the tested reconciliation and no-retransmission properties under the recorded scenarios.
- `READY_FOR_CANARY` is a qualification disposition, not evidence that a canary, deployment, promotion, or production workload succeeded.
- No novelty claim is made. Any novelty claim requires a literature review and comparison with prior work.

## Candidate future experiment

For R5 or post-canary research, preregister a state-machine fault campaign that varies the crash point across local intent persistence, request transmission, remote commit, receipt publication, local ACK persistence, and restart reconciliation. For each operation, retain an ordered network-action trace and authoritative/local state snapshots. Include receipt-found, receipt-absent, lookup timeout, malformed receipt, stale receipt, concurrent restart, and repeated-restart cases. Primary checks should separately report receiver effect count, sender `POST` count after ambiguity, local terminal state, and convergence latency. This is a proposed experiment only; it was not executed as part of this documentation work.

## Paper-ready finding statement

In the R4 qualification of candidate `eada7577cf6f2de875b508c6a82f47870e3aa673`, a lost acknowledgement after remote commit followed by sender restart produced a retransmission before authoritative receipt reconciliation. Receiver-side idempotency limited the observation to one receiver event, but did not satisfy the stronger sender-side invariant of zero retransmission after an ambiguous committed outcome. R4.1 separated an unrelated G11 instrumentation error from this protocol defect, repaired restart recovery to perform authoritative receipt lookup before retransmission, and qualified candidate `8701367db6d3202f24b3eb9f4696b0cadf657985` (tree `79bfe6ed1743907065ed44aeb9c460c47527e0c6`) across receipt-found, receipt-absent, reconciliation-unavailable, and repeated-restart branches. The complete 17-gate R4.1 run passed and was disposed `READY_FOR_CANARY`. These results are bounded to the recorded qualification conditions and do not support a claim of novelty without literature review.
