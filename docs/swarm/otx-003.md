# SPEC-SWARM-OTX-003 — Orchestration Tax Controller

Branch: `swarm/otx-003-orchestration-tax`
Implementation: `residual/otx/` · Tests: `tests/swarm/test_otx.py` · Evidence: `evidence/otx/`

## Design summary

`OrchestrationTaxController` learns when swarming helps and when orchestration
overhead exceeds its benefit:

- **Decomposed timing (R1)** — `PhaseTiming` records planning, scheduling,
  context packaging, worker execution, verification, integration, and
  coordination separately; `observed_tax()` = coordination overhead /
  worker execution.
- **Data-derived tax (R2)** — `orchestration_tax(task, topology)` returns the
  posterior-mean tax for the task's class and topology; nothing is a fixed
  constant (priors are structural only and are dominated by data).
- **Bayesian updating (R3)** — `NormalInverseGamma` posteriors for tax and
  worker seconds, `BetaRate` posteriors for reliability, all keyed by
  (task_class, topology); uncertainty (`tax_std`) is carried into every
  prediction.
- **Predicted vs observed (R4)** — `record_outcome` attaches a
  `TaxComparison` (predicted, observed, error, within-1-std) to every
  experimental observation.
- **Deployment threshold (R5)** — `ControllerConfig.deployment_tax_threshold`;
  when the utility winner's predicted tax exceeds it, the controller walks
  down the complexity order (swarm → pair → single) to the simplest topology
  within budget, and records `selection_reason="deployment_threshold"`.
- **Granularities (R6)** — `FrozenWorkloadFixture` (local minimal fixture,
  hash-bound, seeded) spans atomic/composite/project granularities;
  `from_eval_workload` is the adapter for Swarm A's EVAL-001
  `FrozenWorkload` schema (integration point — Swarm A owns the full schema).
- **Quality-adjusted utility (R7)** — `utility = P(correct) × value −
  latency_penalty × predicted_total_s`; a faster-but-less-reliable topology
  cannot win on latency alone (see test).
- **Observations (R8)** — every `select_topology` call appends a
  `TopologyObservation` with inputs (task + config), per-candidate predicted
  utility/tax, a hash of the estimator snapshot, selected topology, and the
  eventual observed result.

## Integration points

- Engine selection remains with `residual.engines.router.CapabilityRouter`;
  this controller chooses *topology* (roles/worker count), not engines.
- Run lifecycle hooks: `residual.async_io.coordinator.AsyncRunCoordinator`.
- Production per-phase timings come from station scheduling
  (`residual.station`); callers feed them to `record_outcome`. The bundled
  `simulate_execution` is a seeded development fixture (non-live, cf.
  EVAL-R10's scripted-fixture rule).

## Evidence (Gate B)

`python3 -m residual.otx.evidence` writes:

- `evidence/otx/results.json` — artifact version, git commit/tree identity,
  Python/platform versions, controller config, frozen workload hash + seed,
  per-granularity evaluation metrics, learned per-class preferences, replay
  verification, observation count, and SHA-256 of the observation stream.
- `evidence/otx/observations.jsonl` — the raw observation log (JSONL),
  hash-linked from `results.json` via `observations_sha256`.

The `identity.git_commit`/`git_tree` fields record the exact checkout the
study was executed on. Reproduction: `residual.otx.replay.verify_replay`
folds stored outcomes in sequence order and re-derives every decision; the
shipped artifact reports `replay.exact: true` (24/24 decisions).

Acceptance result on the frozen fixture: `lookup → single`,
`synthesis → swarm` (two task classes, distinct preferred topologies).
