# SPEC-SWARM-DSM-004 — Distributed State Maturity

Status: implemented (branch `swarm/dsm-004-distributed-state`)
Module: `residual/dsm/` — Tests: `tests/swarm/test_dsm.py` — Evidence: `evidence/dsm/dsm-004-evidence.json`

## Design summary

`residual/dsm` is a self-contained distributed-state layer built around a
durable, hash-chained, monotonic-sequence **journal** (`journal.py`). All
accepted state transitions are appended (with `fsync`) before any
acknowledgement is returned, and every consumer-visible property —
deduplication, projections, conflict resolution, provenance — is derived
from the journal alone, so replay after a crash is byte-for-byte
deterministic.

Components:

| Component | File | Guarantees |
|---|---|---|
| `OwnershipRegistry` | `ownership.py` | One authoritative writer role per domain; foreign writes fail closed (R1). |
| `Journal` | `journal.py` | Durable append, monotonic `seq`, hash chain, cursor replay, integrity verification (R2/R3/R8/R9). |
| `LeaseManager` | `lease.py` | Monotonic per-resource fencing tokens; stale/expired/foreign tokens fail closed (R5). |
| `Outbox` / `Inbox` / `AckLog` | `delivery.py` | At-least-once delivery with durable acks; exactly-once *effect* via durable dedupe (R2/R3/R4). |
| `DistributedStateStore` | `store.py` | Admission pipeline (dedupe → ownership → fencing → terminal legality), deterministic conflict resolution, crash-point injection (R1/R4/R5/R6/R8/R9). |
| `FaultSchedule` / `FaultyChannel` | `faults.py` | Deterministic duplicate/delay/reorder/loss injection (R10). |
| `run_recovery_suite` | `recovery.py` | Restart/replay scenarios proving no duplicate accepted transition (R8/R9, acceptance). |
| `generate_evidence` | `evidence.py` | Machine-readable evidence bound to git commit/tree identity (gate B). |

### Authoritative ownership (R1)

| Domain | Authoritative writer |
|---|---|
| `task.lease` | `scheduler` |
| `receipt.publication` | `verifier` |
| `integration.intent` | `integrator` |
| `task.terminal` | `orchestrator` |

Terminal states (`succeeded`, `failed`, `rejected`, `unknown`) are
absorbing; `UNKNOWN`/`FAIL`-family states remain distinct per the program's
shared rules.

### Deterministic conflict semantics (R6)

The journal's `seq` gives every accepted event a total order. Concurrent
conflicting values for the same `(domain, entity)` resolve to
**argmax(fencing_token, writer, event_id)**, computed from the journal
alone. Live execution and any number of independent replays converge to
identical projections — no consensus protocol is needed because there is a
single journal (single-writer log), not multiple acceptors.

## Consensus boundary (R7)

### Properties guaranteed **without consensus** (single durable journal)

These hold today, provided there is exactly one journal writer at a time
(enforced by process-level exclusivity of the journal file) and storage
honors `fsync`:

- **Durable acknowledgement** — an ack is returned only after the record is
  fsynced; unacked sends are retransmitted from the durable outbox (R2).
- **Reconnect/catch-up** — replay from any durable cursor over the
  monotonic sequence (R3).
- **Idempotent delivery** — dedupe is derived from the durable journal, so
  duplicates never produce a second accepted transition, even across
  restart (R4).
- **Fencing fail-closed** — *given an accurate lease table*, a stale
  fencing token is always rejected (R5).
- **Deterministic conflict resolution** — total order from journal seq plus
  the argmax tie-break rule; replay-stable (R6).
- **Crash recovery & provenance** — accepted transitions and their audit
  metadata (writer, fencing token, hash chain) are fully recomputed from
  the retained journal (R8/R9).
- **No duplicate accepted transition across restart/replay** — proven by
  the deterministic recovery suite (acceptance, gate C).

### Properties that **require consensus** (a consensus service)

These are explicitly **not** claimed by this implementation:

- **Split-brain-free lease leadership.** The `LeaseManager` lease table is
  in-memory per store. If two store processes run against shared state with
  independent lease tables, two holders can believe they own the same
  lease; fencing tokens then fail closed only within one table. Making
  lease acquisition itself safe under network partition **requires
  consensus** (e.g. Raft/etcd-backed leases) so that fencing token
  issuance is linearizable.
- **Multi-node linearizable writes.** With more than one journal writer
  (active-active), there is no total order; cross-node conflicts would need
  a consensus-decided log. This layer is single-writer by design.
- **Durable availability under replica failover.** The journal is a local
  file; surviving loss of the whole machine needs synchronous replication
  decided by consensus.
- **Linearizable read-your-writes for external observers.** Projections are
  local; a remote reader racing a failover may observe stale state until
  catch-up completes.

Remaining non-consensus guarantee summary: everything in the first table
holds under crash-stop faults and arbitrary delivery faults (duplicate,
delayed, reordered, lost) for a single-writer deployment; nothing in the
second table is claimed.

## Evidence (gates B & C)

`evidence/dsm/dsm-004-evidence.json` (regenerate with
`python3 -m residual.dsm.evidence`) contains:

- exact source identity: git commit, tree hash, branch, Python/platform;
- the fault schedules and delivery traces for every fault-matrix case
  (duplicate, delayed, reordered, lost, combined);
- the recovery-suite scenarios including **process death between journal
  write and acknowledgement**, with raw event logs from every journal;
- results proving `no_duplicate_accepted_transition` across all
  restart/replay scenarios and identical accepted-state sets under faults.

Gate C: `run_recovery_suite` recomputes accepted state transitions from the
retained journal alone in three scenarios and proves the accepted
`event_id` set contains no duplicates; the same recomputation is asserted
independently in `test_gate_c_recompute_accepted_transitions_from_journal`.
