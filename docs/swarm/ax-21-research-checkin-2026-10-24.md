## 2. New negative-to-repair: WebVM projection rehashes the wrong bytes

**Observed source-level contradiction:** In `residual/storage.py`, `Ledger.add` computes the SHA-256 over the canonical event **before** adding its top-level `sha256` field. At #543, `verifyEvidenceChain` in `demo/vm/mission-control.js` hashes the canonical projected event **including** that field and then compares the result with the original digest. These are different byte strings. A valid guest ledger event therefore yields a browser `digest mismatch` (a false negative) without any guest-ledger corruption.

**Independent bounded check performed for this entry:** A disposable Python synthetic canonical event following the inspected `canonical` sorting and `Ledger.add` field order returned `original_verifier_matches=False`, `corrected_verifier_matches=True`, `mutated_matches=False`. This is an independently computed **synthetic** cross-check of the byte-order hypothesis, not an execution of a built WebVM/actual browser or a release artifact.

**Successor #544:** Removes the unique canonical top-level `sha256` field immediately before `time_ns` without reserializing nested data/number encodings, then hashes the original committed bytes. The new test executes the shipped JS verifier on real Python Ledger events, checking one valid root and a tampered-event negative. In [Command Station run 40077120683](https://github.com/ninja-ops-guy/residual-agent-harness/actions/runs/40077120683), the Python 3.13 job log explicitly reports `test_shipped_browser_verifier_matches_ledger_and_rejects_tamper ... ok`; its **1,204-test job remains FAIL** (one inherited Node diagnostic failure, 22 skips). The author records a direct Node positive/negative probe; full-browser replay is NOT independently established here.

**Falsified assumption:** A display-side chain verification result automatically agrees with the guest's authoritative ledger proof. **Not established:** independent authenticity of a guest-projected history; the projection and reported root come from the guest, while `trace.jsonl` / `verify-trace` remain the canonical integrity surface. The fix is a bounded source-level verifier repair, not evidence of a general security property.

## 3. New evidence-retention boundary: stronger observability can enlarge persistence scope

**Observed:** #543 adds `Harness(..., retain_content=False)` by default and explicitly turns retention on for workbench/browser missions, adding `run_started.goal`, `call_reserved.packet`, `call_completed.response_text`, `verification.message`, and `obligation_accepted.value` into the ledger. The UI persists projected frames per conversation to browser `localStorage` under `residual.chat.evidence.v1.*`, with a nominal 300,000-character cap, quota catch, and a `truncated` flag. Restoration can show a truncated **prefix** without comparison to the complete root; the UI labels it as truncated. No explicit retention expiry, purge-on-new-chat, or delete-all-content contract was located in the inspected `mission-control-world.js` path. This is **not** evidence of an exploit or an observed leak.

**Interpretation and negative control needed:** Content-binding improves operator-visible semantic evidence relative to hashes-only views, but integrity of retained bytes does not itself establish that the bytes are authentic, safe to persist, necessary to retain, or later completely reconstructible after truncation. Remote-call consent is distinct from consent to persistent browser storage. LocalStorage persistence, UI trust status, truncation, retention, deletion and sensitive-data handling require a separate privacy/storage-lifecycle review. Do not claim the change is security-neutral merely because the previous provider consent gate remains.
