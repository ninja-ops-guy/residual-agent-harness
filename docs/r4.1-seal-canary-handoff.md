## Findings

### R4-F01 — qualification instrumentation defect

`Station.prepare()` persisted `candidate_dir` into authoritative task storage but returned an earlier task snapshot. The original G11 consumed `work["task"]["candidate_dir"]` immediately after `prepare()`. R4.1 corrected the instrument to reload authoritative task state before constructing the protected-path sentinel.

This is **not a candidate security defect**. The repaired gate demonstrated rejection of both a tool-shaped response and a protected runtime write, with the sentinel unchanged.

### R4-F02 — candidate protocol defect

The original lost-ACK recovery path retransmitted after sender restart before authoritative reconciliation. Receiver-side idempotency prevented duplicate receiver events, but did not by itself establish sender-side crash/restart reconciliation safety.

The repaired recovery path performs `GET comms/receipt` before deciding whether retransmission is necessary. R4.1 validated receipt-present, receipt-absent, reconciliation-unavailable, repeated-restart, and full lost-ACK qualification branches. R4-G13 passed.

## Canary boundary

The minimum useful live canary is exactly one pre-authorized Shared Comms operation with one stable `operation_id`, a crash-durable outbox, an experiment-owned sender interruption, and receipt-first restart reconciliation. It must be bounded to one initial POST, one receipt lookup after restart, and a 120-second total timeout.

The canary must fail closed unless all of the following hold:

- exact candidate HEAD/tree/parent, clean worktree, and no Git remotes;
- verified R4.1 seal and explicit operator GO;
- scoped, unexpired authorization receipt bound to the operation ID;
- new safe evidence destination and deployment-specific adapter preflight;
- expected protected-service state and independently invocable rollback.

Success requires complete hash-bound evidence, exactly one receiver event, `PENDING → SENT_INDETERMINATE → ACKED`, receipt GET before any recovery decision, zero retransmission POST after restart, stable protected services, and zero safety-counter changes. Verification dispositions are `CANARY_PASS`, `CANARY_FAIL`, or `EVIDENCE_INCOMPLETE`. `CANARY_PASS` cannot deploy, merge, promote, or push.
